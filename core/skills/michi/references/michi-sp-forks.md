# michi — forks SP vs repo (Phase 1)

- **SP vs repo state may still fork (atlas michi cycle 2026-09-04, Epic A polish).** A SP can be internally consistent and STILL conflict with current repo reality. Two real forks the SP missed: (a) **dirty `dev`** — the SP said "create worktree from dev", but `dev` had 9 files dirty from a previous unfinished session. Forcing a worktree off dirty `dev` mixes scopes; the user must choose: commit the orphan work to a feature branch first, stash it (lose), or carry it into the new worktree (don't). (b) **SP-stated worktree path vs repo convention** — the SP said `code/.wt/atlas/polish-A-foundations/` with a manual branch name; the actual repo convention is `live-data/.wt/atlas/<hash>/` (worktree manager auto-named). Follow SP literally or follow repo practice? **Recipe:** before DP sign-off, scan the actual repo (`git status`, `git worktree list`, `git branch -a`, ls of worktree dirs) and surface any SP-stated fact that disagrees with the scan. Batch into ONE free-text ask (not multi-choice), alongside the DP draft. Honour each fork as the user decides; the SP is a contract for INTENT, not for paths that the repo has its own opinion about.

- **SP §2 stack supersede can disagree with §7 scope (atlas-mundo-workflow michi, 2026-09-05).** §2 sets INTENT (stack, files to touch, prior decisions); §7 enumerates STEPS. When §2 supersedes a prior stack decision ("React+Tailwind+shadcn for new UI, supersedes the frozen vanilla") but §7 doesn't list the rename/migration that the supersede implies (e.g. `notes-vanilla.ts → notes.tsx`), the DP has THREE options and the user must choose: (a) honour §2 literally and add the rename as a step; (b) honour §2 spirit (new UI = React) but keep the existing file (`notes-vanilla.ts` stays vanilla, new code lives in `notes.tsx`); (c) defer §2 to a follow-up SP and ship vanilla-only in this cycle. **Recipe:** in the DP's "What you should know before signing off" section, name the §2-vs-§7 gap as a single free-text fork. Default = (b) when the existing file is the substrate (most refactor-friendly, lowest churn). Anti-pattern: silently honour §2 (full rename, no §7 step → uncommitted rename mid-DA) or silently ignore §2 (vanilla-only when the SP said React → user sees drift at the first review). The SP is intent; the DP is the negotiated contract; the fork lives there, not in DA.

- **No fork in pre-DA state gate = no ask (atlas-mundo-workflow michi, 2026-09-05).** The pre-DA state gate's output is "all clear, proceeding" OR "fork: X" — not always a question. When `git status --short` (in the right repo root), `branch --show-current`, and `log -1 --oneline` ALL match the SP's claims AND the dependency check passes (package.json contains every claimed dep), the DP proceeds directly to "What you should know before signing off" without a free-text ask. Cost of asking anyway: one wasted round-trip for "yep, proceed". The fork-trigger is "ANY fact disagrees" — single disagreeing fact = ask; zero disagreeing facts = proceed. Companion: the user will tell you if they want to be asked even on clean state — the default is no.
